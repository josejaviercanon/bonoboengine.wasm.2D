# ADR-009: Strip Blazor Components for browser-wasm Native-AOT Host

**Date:** 2026-09-02
**Status:** Accepted (supersedes RCL/SSR pipeline in ADR-007/ADR-008)

## Context

The previous architecture used `Game.Wasm` as a **Blazor WebAssembly host** (`Microsoft.NET.Sdk.BlazorWebAssembly`). This pulled in the full Blazor component runtime (`Microsoft.AspNetCore.Components.WebAssembly`, Razor compilation, virtual DOM diffing), even though the engine already used zero-copy shared-memory interop (ADR-008) and never relied on Blazor for rendering (PixiJS owns the canvas). The Blazor components served only:

1. An SSR shell (`ExampleHost.razor`) that serialized initial snapshots into `data-message` attributes.
2. An examples catalog UI (`ExampleToolbar.razor`, `ExamplesHome.razor`) rendered with Razor dynamic components.

All hot-path rendering, simulation, and input went through `wasm-interop.js` + pinned memory — never through `IJSRuntime` or Blazor component lifecycle. The Blazor shell added ~2 MB of AOT-unsafe framework assemblies (reflection-heavy DI, JSInterop marshaling, component metadata), increased WASM payload, and prevented aggressive trimming.

## Options Considered

1. **Keep Blazor shell** — minimal work but continues shipping dead assemblies; `WasmStripILAfterAOT` cannot remove them because Blazor's own reflection entry points are still reachable.

2. **Strip Blazor, use `Microsoft.NET.Sdk.WebAssembly`** — replace Blazor WASM SDK with the direct, non-Blazor browser-wasm SDK that produces a trimmed `dotnet.{wasm,js}` bundle without the component pipeline. This SDK (available in .NET 9/10) sets `RuntimeIdentifier=browser-wasm`, imports `StaticWebAssets`, and runs via `WasmAppHost` during development.

## Decision

**Option 2 — Strip Blazor, migrate to direct browser-wasm host.**

### Implementation Summary

| Change | Before | After |
|--------|--------|-------|
| `Game.Wasm` SDK | `Microsoft.NET.Sdk.BlazorWebAssembly` | `Microsoft.NET.Sdk.WebAssembly` |
| `Game.Wasm` packages | `Microsoft.AspNetCore.Components.WebAssembly` + DevServer | None (SDK intrinsic) |
| `Game.Wasm` entry | `WebAssemblyHostBuilder` + `RootComponents.Add<App>` + `host.RunAsync()` | `public static void Main()` → direct `WasmInterop.Initialize(new SimHost())` |
| `Game.Wasm` boot JS | `blazor.webassembly.js` + `Blazor.start()` | `import { dotnet } from './_framework/dotnet.js'` → `.create()` → `setModuleImports(...)` → `runMain()` |
| `Game.UI` SDK | `Microsoft.NET.Sdk.Razor` | `Microsoft.NET.Sdk` (plain class library, no Blazor refs) |
| `Game.Examples` SDK | `Microsoft.NET.Sdk.Razor` | `Microsoft.NET.Sdk` (plain class library) |
| Razor components | `App.razor`, `Routes.razor`, `Layout/MainLayout.razor`, `GameView.razor`, `ExamplesHome.razor`, `ExampleHost.razor`, `ExampleToolbar.razor`, `Component1.razor` | Deleted (replaced by static Tailwind toolbar built by `main.mjs`) |
| Example payload delivery | SSR via `data-message` attribute from `ExampleHost.razor` | Client-side fetch via `[JSExport] string GetExamplePayload(string id)` (JSON, source-gen AOT-safe) |
| Asset serving | `_content/Game.UI/...` (RCL static-web-asset path) | `./dist/...`, `./audio/...` (Game.UI assets copied into Game.Wasm/wwwroot via MSBuild target) |
| AOT/trim props | `RunAOTCompilation`, `WasmStripIL` | Added `InvariantGlobalization`/`InvariantTimezone`/`TrimMode=full`/`WasmGenerateAppBundle` |
| E2E host | `Game.Web` (nonexistent) | `Game.Wasm` via `dotnet run` with `ASPNETCORE_URLS=:5902` |

### AOT Strategy

The non-Blazor `Microsoft.NET.Sdk.WebAssembly` produces a fully relinked WASM binary with the Mono interpreter. AOT is enabled via `RunAOTCompilation=true` (Release), `WasmStripILAfterAOT=true`. Source-generated `JsonSerializerContext` replaces reflection-based `System.Text.Json` serialization for the example payload — safe under aggressive trimming.

## Consequences

- **Positive:** Zero Blazor component assemblies in the WASM bundle. Startup downloads ~2 MB less framework code. Trimming more aggressive (`TrimMode=full`).
- **Positive:** Direct `[JSExport]` entry eliminates DI container + `IJSRuntime` marshaling overhead. Program.Main allocates nothing beyond `SimHost`.
- **Positive:** E2E test suite now boots the real `Game.Wasm` host on a fixed port. Faster iteration.
- **Positive:** `Game.UI` and `Game.Examples` are plain class libraries — easier to AOT-verify and avoid accidental Blazor dependency.
- **Negative:** `Game.Maui` (commented out of the solution) references `Game.UI` and `Game.Examples`. If re-enabled, MAUI's `Components/` will need their own Blazor components (not affected by this ADR — web-only builds remain the default).
- **Negative:** Example payloads are now fetched from C# after WASM boot, so the first scene render waits for `runMain()`. WASM cold-boot latency applies before any game appears (previously SSR gave immediate data-message). Mitigated by generous E2E timeouts (60s).
- **Negative:** Asset paths changed from `_content/Game.UI/...` to `./...`. Scene TS source updated in 6 files (10 occurrences). Must keep `Game.UI/wwwroot` in sync with the copy target.
