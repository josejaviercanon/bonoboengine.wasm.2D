# ADR-008: Zero-Copy Shared Memory Interop Pipeline

**Date:** 2026-09-02
**Status:** Accepted (supersedes ADR-007 Phase 2 byte-array transport)

## Context

The ADR-007 Phase 2 `DirectRenderTransport` delivered float32 signal buffers via `byte[]` → Blazor `InvokeVoid("onRenderSignalBuffer", bytes…)` — a per-frame copy from C# to JS (byte[] marshaling, base64 fallback). This copy overhead capped throughput and violated the zero-copy principle mandated by the shared-memory architecture. The command path used `DotNetObjectReference` + JSON string serialization for every input event.

## Options Considered

1. **Keep byte-array Blazor interop** — simplest change, but still copies every frame. The Blazor byte[] marshaling creates a C#→JS copy even with `IJSRuntime`. Does not eliminate GC pressure.

2. **MemoryView via `ArraySegment<byte>`** — `.NET`'s zero-copy marshaling for `ArraySegment<byte>` via `JSMarshalAs<JSType.MemoryView>`. JS gets a `MemoryView` object (not `Float32Array`) — scenes expect `Float32Array`, requiring either a scene change or a wrapper layer.

3. **Raw pinned pointer + `[JSImport]` notify → JS reads over WASM heap** — pin a `float[]` via `GCHandle`, export the `(ptr, len)` via `[JSExport]` or pass directly to `[JSImport]("notifyRender")`. JS reads `new Float32Array(heap.buffer, ptr, count)` via `getDotnetRuntime(0).localHeapViewF32()`. Zero copies. JS reads the same linear memory region the C# encoder writes into.

## Decision

**Option 3 — Raw pinned pointer + `[JSImport]` notify.**

Implementation:
- `PinnedRenderBuffer` (in `Game.Engine/ECS/`): pinned `float[]`, `GCHandle`, provides `Span<float>` for `DirectRenderTransport` to encode into. Zero copy from encode → JS.
- `DirectRenderTransport` rewritten: encodes into `PinnedRenderBuffer`, calls `Commit(eventName)` which triggers `[JSImport]("notifyRender", "WasmInterop")` passing `(ptr, floatCount)`.
- `WasmInterop` (in `Game.Wasm/`): static partial class with `[JSImport]`/`[JSExport]` methods. Replaces both `WasmRenderBridge` and `CommandHandler`.
- `wasm-interop.js` module: exports `notifyRender`, reads pinned buffer via `getDotnetRuntime(0).localHeapViewF32()`, dispatches `Float32Array` to provider listeners.
- Commands: typed `[JSExport]` methods per game input (primitives only — no JSON). Scene-side `postCommand(path, bodyJson)` parses JSON in JS, passes primitives to C#.

## Consequences

- **Positive:** True zero-copy per-frame render transfer. One primitive `[JSImport]` call per signal (no byte/serialization overhead). Commands eliminate JSON deserialization in C# (AOT-safe, no `DotNetObjectReference`).
- **Positive:** No runtime reflection on the hot path. `[JSImport]/[JSExport]` are Roslyn source-generated (AOT-safe, IL-trim-compatible).
- **Positive:** Scenes unchanged — they receive the same `Float32Array` through the same `provider.onSignal` API. `bufferLayout.ts` decoders unchanged.
- **Negative:** Requires `AllowUnsafeBlocks=true` for the source generator.
- **Negative:** JS must re-fetch `localHeapViewF32()` per notify because WASM memory growth invalidates the `ArrayBuffer`. The pinned pointer offset remains valid across growth.
- **Negative:** Removed `CommandJsonContext` — `RacerConfigRequest` now passes 7 primitives via a single `[JSExport]` method instead of JSON deserialization.
